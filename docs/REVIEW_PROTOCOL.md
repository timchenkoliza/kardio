# Протокол проверки обновлений Kardio

Утверждено владельцем продукта 24.10.2026. Протокол действует для каждого изменения, которое видит врач, и для каждого релизного среза.

## Кто проверяет

**Продуктовая команда — три независимых ревьюера.** Каждый получает один и тот же SHA, исходные материалы, маршруты, скриншоты и код. Работают параллельно и не читают отчёты друг друга.

| Ревьюер | Роль | Файл роли | Что отвечает |
| --- | --- | --- | --- |
| A | Взаимодействие | `.claude/agents/apple-product-interaction-architect.md` | Понятно ли главное, первичное действие, обратная связь, путь назад, 390 и 768 px |
| B | Информационная архитектура | `.claude/agents/google-workspace-information-architect.md` | Где живёт функция, связи «вопрос → ответ → материалы», состояния и настройки |
| C | Клинический | `.claude/agents/clinical-evidence-reviewer.md` | Источник и дата у каждого утверждения, честный статус проверки, граница применимости, нет назначений пациенту, нет утечки ПДн |

Если реестр агентов сессии не видит файлы ролей, ревьюеров запускают как `general-purpose`: первой инструкцией каждый читает свой файл роли и работает по его тексту (см. `docs/ux-remediation/ISSUE_LEDGER.md`, «Как запускались субагенты»).

**Инструмент владельца — восемь персон (PR #19).** Вызывается командой `/product-council` (`docs/PERSONA_PRODUCT_COUNCIL.md`). В продуктовую команду не входит и проверку A/B/C не заменяет.

## Обязательный гейт — каждое обновление

Без зелёного гейта изменение не идёт в релизный срез. Результат записывается в сообщение коммита или в отчёт раунда вместе с SHA.

1. **Язык и DS:** `npm run lint`. Он включает ESLint, `scripts/check-design-tokens.mjs` (только токены Yandex Med DS: никаких сырых цветов, радиусов и шрифтов) и `scripts/check-product-copy.mjs` (правила текста). Для изменений интерфейса дополнительно запускается `ds-auditor` (`npm run ds:audit -- --url <preview> --no-ai`).
2. **Типы:** `npm run typecheck`.
3. **Unit:** `npm test`. Регрессионный набор раундов — `tests/unit/ux-remediation.test.tsx` — проходит целиком.
4. **Маршруты и слова на корпусе вопросов**, до и после изменения:
   ```
   git worktree add /tmp/kardio-base <base-sha>
   (cd /tmp/kardio-base && npx tsx <repo>/scripts/route-corpus.ts > /tmp/routes-old.tsv)
   npx tsx scripts/route-corpus.ts > /tmp/routes-new.tsv
   npx tsx scripts/route-corpus.ts --compare /tmp/routes-old.tsv /tmp/routes-new.tsv
   ```
   Каждое изменение маршрута (ROUTE) и распознанных слов (WORDS) должно быть намеренным и объяснённым. Непредвиденное изменение — дефект.
5. **Интеграционные на PostgreSQL:** `npm run test:integration`. Нужны миграции и сохранение состояния.
6. **Сборка:** `npm run build`.
7. **Живая проверка** изменённого сценария на собранном сервере. Для релизного среза — `npm run test:e2e` целиком на том же SHA.

Проверка, которая не запускалась, не считается пройденной. Если окружение не позволяет её выполнить (нет сети к источнику, нет браузера), это записывается как «не проверено» с причиной.

## Порядок раунда

1. Автор фиксирует SHA и проходит гейт.
2. A, B и C проверяют этот SHA независимо: каждый выдаёт не больше десяти находок P0/P1/P2 с шагами и проверяемым критерием приёмки.
3. P0 и P1 исправляются. Затем повторный раунд на новом SHA — только по затронутым находкам и с тем же гейтом.
4. Релиз — без известных P0/P1. Некритичные P2 записываются в журнал и не блокируют выпуск, если пользователь не получает ложных обещаний.
